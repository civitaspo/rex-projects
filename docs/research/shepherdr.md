# Shepherdr applicability to rex-projects

**Research date:** 2026-11-05
**Upstream revision reviewed:** [`35af6d7fc9b709fb8773c52d24595a4056af2428`](https://github.com/eliasstravik/shepherdr/commit/35af6d7fc9b709fb8773c52d24595a4056af2428) (main at review time)

## Summary

Shepherdr is an agent orchestration product built specifically as a Herdr app layout and companion service. Rex itself has a documented Lua scripting API that can call commands, create terminal layouts, and react to terminal events, so a Rex-facing terminal workflow is technically feasible. The current `rex-projects` checkout is a separate, small repository of Lua static-analysis rules and project tooling; it contains no Rex runtime or task controller. Shepherdr is therefore a workflow reference, not a drop-in dependency or a supported backend API for Rex.

## Rex integration surface

**Observed facts:** Rex itself has a Lua API and a CLI. Lua scripts run with `rex do`, can call `rex.exec` for local commands, and can create windows, splits, and terminal blocks through `rex.session.new_window` / `new_split`. Scripts can subscribe to terminal and session events with `rex.on` or wait with `rex.wait`; documented terminal events include child exit, process changes, progress reports, and program status changes. Event handlers run in scripts; they are not a generic task-state feed. Rex runs Lua 5.1, disables `io.popen` and `os.execute`, and directs scripts to use `rex.exec`. [Rex Lua API](https://www.superlogical.com/rex/docs/reference/lua) · [Rex Lua scripts](https://www.superlogical.com/rex/docs/automate/lua-scripts) · [Rex events](https://www.superlogical.com/rex/docs/reference/events)

**Feasibility:** A Rex-facing prototype is feasible without changing Rex: a custom Lua action can call a Rex-side task controller via `rex.exec`, open one terminal block per task, and combine Rex terminal events with explicit controller task state to refresh labels or move focus. Task-specific states such as “needs review” would need to come from the controller (or an explicit program-status protocol); Rex's documented terminal events do not describe Shepherdr task state. The API directly supports command execution and terminal/session layout, but its documented Lua surface is centered on sessions, blocks, and terminals. It does not expose Shepherdr's task objects or a task-board widget. A standalone task board would need Rex's separately documented plugin/block extension route or an external UI/service. [Rex Lua API](https://www.superlogical.com/rex/docs/reference/lua) · [Rex Lua scripts](https://www.superlogical.com/rex/docs/automate/lua-scripts) · [Rex events](https://www.superlogical.com/rex/docs/reference/events)

**Boundary:** `rex-projects` is a separate repository of project rules and tooling, not Rex's runtime. Its current source can define and lint project-owned Lua scripts, but cannot add methods to Rex's server from within this repository. Any adapter would be a new Lua/configuration artifact that a Rex installation loads, plus a task controller or CLI it invokes. This separates the integration surface Rex documents from the capabilities present in this checkout.

## User-facing workflow insights

- **Model task state as actionable buckets.** Shepherdr's task model exposes `Needs you`, `Ready`, `Merging`, `Working`, `Queued`, `Scheduled`, `To do`, and `Done`. A blocker goes to `Needs you` only while no non-reviewer agent is actively fixing it; `Ready` means the agent finished and presents a separate human review/accept action. This makes “work is happening” distinct from “the person must act.” [Pinned task-state source](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056af2428/core/tasks.js) · [Pinned task-panel parity guide](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056/docs/parity/tasks.md)
- **Make waiting reasons legible.** Queued work explains whether it waits for named prerequisites, a per-folder concurrency limit, or machine capacity; scheduled work shows its start time and time remaining. The source sorts scheduled tasks by earliest start, todo tasks by creation order, and most active states by recent activity. [Pinned task-state source](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056/core/tasks.js)
- **Treat attention priority and execution order as different controls.** A pinned task appears in a Pinned group; it does not itself preempt work. Dependencies, scheduled start time, per-folder `max_running`, and machine capacity determine what can start. This is a useful distinction for Rex UI: a personal “keep visible” marker should not silently imply scheduler priority. [Pinned task-state source](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056/core/tasks.js) · [Pinned settings guide](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056/docs/settings.md)
- **Keep a review gate concrete.** Shepherdr's default merge mode is “ask”; the Ready row's Review button opens an Accept card, and per-space settings can tune merge and review behavior. The README cautions that instructions and reviews are not a sandbox. A Rex prototype should surface the intended next action and the evidence before acceptance, while keeping execution permissions grounded in Rex/agent security controls. [Pinned settings guide](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056/docs/settings.md) · [Pinned task-panel source](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056/mods/tasks/main.js) · [Pinned README](https://github.com/eliasstravik/shepherdr/blob/35af6d7fc9b709fb8773c52d24595a4056/README.md)

## Rex API feasibility and recommendation

**Feasibility now:** Rex's documented Lua API makes a terminal-oriented adapter technically plausible, but this checkout does not contain a Rex runtime, adapter, task model, or executable. Shepherdr's internal HTTP routes are not a supported interchange contract, so an adapter should call a purpose-built controller/CLI or another documented interface rather than bind to `/api/*`. The actual task and review behavior would need to be implemented by that controller; Lua rules in this checkout only lint code and do not supply it.

**Recommendation:** If Rex is intended to host an agent task workflow, start with a narrow Rex Lua action that delegates to a Rex-owned CLI/controller, opens task terminals, and reports on explicit lifecycle events. Keep task state and scheduling in that controller; use Rex's Lua API for integration with sessions and terminals. Add a native task board only if Rex's block/plugin route supports the required interaction model. Shepherdr is a strong workflow reference for actionable status buckets, queue reasons, human review, per-folder limits, and machine-capacity awareness. These are recommendations; the checkout contains no declared Rex roadmap, and its initially clean status showed no uncommitted product direction.
